# ADR-0013 — The front end is UI Toolkit, generated from the V2 mockups

**Status:** Accepted
**Date:** 2026-10-19
**Deciders:** shobhit

## Context

The V2 design ([ADR-0011](ADR-0011-adopt-v2-design-prototype-first.md)) now lives in a Design
canvas (`Slap Mania Game UI`). It holds 28 V2 screens plus a UI kit, and 16 V1 screens. The
in-match screens (C4–C6, D1–D3, E2/E3) already exist as the uGUI `V2Hud` (M10). The owner asked
for every other screen in the game, "pixel perfect", navigable, with motion, and with
placeholders where systems do not exist yet.

Three facts shaped the decision:

- **The mockups are CSS.** They use absolute positioning plus flexbox rows and columns, grid
  tracks, `border-radius` pills, gradient overlays, `clip-path` skew tags, box-shadow glows
  and inline SVG icons. There are about 900 boxes across the 20 screens this ADR covers.
- **The mockups are static.** Every file has 0 `@keyframes`, `animation` or `transition`
  rules, and its logic is an empty `renderVals() { return {}; }`. All motion is a design
  choice to make.
- **uGUI places boxes by hand.** The HUD's builder needs every flex row resolved by hand into
  absolute `(x, y, w, h)`. `SlapPanel` only fakes `border-radius` with corner cuts.

## Decision

1. **Menus are UI Toolkit; the match HUD stays uGUI.** UI Toolkit lays out with the same
   flexbox engine as CSS (Yoga), so a mockup becomes a UXML tree of the same shape. The HUD's
   tested uGUI views are not rewritten.
2. **Screens are generated, not hand-authored.** `Tools/mockup2uxml` (Python, stdlib only)
   resolves each element's *computed* style and writes UXML with inline styles:
   - the cascade over `kit.css` and the page's `<style>`, inheritance, and `em` units;
   - `text-transform`;
   - grid tracks become wrapped rows with computed widths, and `gap` becomes margins;
   - the CSS strut and half-leading rules for text boxes.

   Inline SVGs become de-duplicated icon files that import as `VectorImage`. Every
   approximation is listed in `Docs/Reference/Mockups/CONVERSION-REPORT.md`. The mockup
   sources are copied into the repo (`Docs/Reference/Mockups/`) so the conversion is
   reproducible.
3. **CSS paint is a Core library.** `SlapMania.Core.Paint` parses and rasterises CSS
   backgrounds, masks, `clip-path` and `box-shadow`, following the CSS Images rules:
   gradient-line length, farthest-corner sizing, premultiplied stop interpolation and
   repeating wraps. It is pure and EditMode-tested (R2/R3). `UI.FrontEnd.PaintBox` renders
   with it: flat colours natively, clip-path shapes as Painter2D vectors, and everything else
   as cached baked textures.
4. **A FrontEnd scene, loaded additively from Boot.** `ScreenManager` (not a singleton) owns
   the stack. UI raises `MatchRequested`, and the App's `FrontEndBridge` asks `GameRoot` to
   swap FrontEnd ⇄ bout. The bout's results return through `GameRoot.RequestFrontEnd`.
   `FrontEnd.unity` is generated by `FrontEndSceneBuilder`, like the prototype scenes.
5. **Motion is authored and tunable.** `UiMotionConfig` (ms, R8) drives screen enter/exit,
   block stagger, press squash, meter count-up, rays, LIVE pulse and the per-screen sequences
   (loader, search, walkout, tape countdown, pack reveal). `VisualTween` is
   `Core.Motion.Tweener`'s sibling for UI Toolkit elements: fixed slots, unscaled time, no
   closures.
6. **Blend like a browser.** The project is Linear (the photo grade needs it), so UI Toolkit
   would blend alpha in linear light. A measured 6 % white glass fill over near-black reads
   70/255 in Unity against 21 in the mockup. `GammaPresenter` therefore renders the panel with
   `forceGammaRendering` into a screen-sized linear RenderTexture, and shows it through a
   one-line decode shader (`SlapMania/UI/GammaComposite`) on a full-screen overlay. Only the
   front end pays for this; the HUD is unchanged.
7. **Mechanics still land as modules (ADR-0011 §3).** Screens show the mockup's copy until a
   module binds real data. V2 words reach code only as screen names (GLOSSARY "Front-end
   screens").

## Consequences

### Positive

- Layout fidelity is a property of the tool. Re-running it after a mockup change regenerates
  every screen, and the report says exactly what is approximate.
- UXML is text: reviewable in a diff and verifiable from code (fewer R11 blind spots than
  scene YAML).
- The CSS paint maths is tested once and reused by every screen.

### Negative

- Two UI systems. HUD work stays uGUI/TMP; menu work is UI Toolkit/TextCore. Fonts are
  shared as TTFs, but text features differ: USS `letter-spacing` does nothing in 6000.3.22f1
  (DEBUG S-076), so tracking is emitted as `<cspace>`.
- Generated UXML should not be hand-edited. Behaviour finds elements through named hooks
  that the converter pins (`HOOKS` in the tool).
- Some CSS has no UI Toolkit equivalent and is approximated:
  - `backdrop-filter` blur;
  - `mask-image` on images;
  - `drop-shadow` on images;
  - the middle stop of gradient text;
  - `saturate(>1)`;
  - `skewX`.

- One screen-sized RGBA render texture plus one full-screen draw while the menus are open
  (about 10 MB at 1080×2400). It is released when FrontEnd unloads.

### Risks

- Baked paint textures cost memory per unique size. The cache shares identical paints, and
  textures die with their screen. Check on device with the Profiler (M10 §10).
- A mockup change that breaks a hook fails the converter loudly. That is intended, not a
  silent regression.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| uGUI for menus, like the HUD | Every flex row hand-resolved to absolute boxes (~900), no true `border-radius`, lower fidelity, slower to change |
| Move the HUD to UI Toolkit as well | Rewrites working, tested HUD code before a single new screen lands |
| Hand-author the UXML | Drifts from the mockups; "pixel perfect" would depend on patience, not on a tool |
| Screenshot each mockup into a texture | Not interactive, no data binding, no motion, huge textures |
| Accept linear blending, or tune colours to compensate | Wrong for every translucent layer at once; a compensation depends on what is underneath, which varies |
| Switch the project to Gamma colour space | Breaks the photo grade the contract requires Linear for |
| Menus inside Boot.unity / one scene per screen | Boot stops being a thin root; per-screen scenes cost a load on every tap (user chose FrontEnd.unity) |
